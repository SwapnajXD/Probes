# Probes

[![CI](https://github.com/SwapnajXD/Probes/actions/workflows/ci.yml/badge.svg)](https://github.com/SwapnajXD/Probes/actions/workflows/ci.yml)
[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE)
![Python](https://img.shields.io/badge/python-3.12-blue.svg)

**A self-hosted service health dashboard** — pings your backends on a schedule, tracks uptime and
downtime incidents with real duration, exposes Prometheus-compatible metrics, and doubles as a
free way to keep low-traffic personal projects from spinning down on free-tier hosts.

🔗 **Live demo:** [probes-794f.onrender.com](https://probes-794f.onrender.com)
📄 **Full technical case study:** [docs/CASE-STUDY.md](docs/CASE-STUDY.md) — the debugging story,
architecture decisions, and what's intentionally left unfinished

---

## What it does

- **Background health checks** — a scheduler thread pings each configured service on a timer and
  records the result
- **Real incident tracking** — not just "is it up right now," but discrete downtime incidents with
  open/close timestamps and computed duration, stored in SQLite
- **Prometheus-compatible `/metrics`** — plugs straight into an existing Prometheus + Grafana stack
- **Environment-variable config resolution** — `${VAR_NAME}` syntax in `services.yaml` keeps
  secrets and per-environment URLs out of committed config
- **Optional Telegram alerting** on status-change transitions, safe no-op when unconfigured
- **Keeps itself and other free-tier apps alive** — the same periodic-ping mechanism that monitors
  other services also prevents *this* app (and whatever it's watching) from idling out

## Running it locally

```bash
python3 -m venv .venv
source .venv/bin/activate      # fish shell: source .venv/bin/activate.fish
pip install -r requirements.txt
python3 app.py
```

Then visit `http://localhost:8080`.

## Running it with Docker

```bash
docker build -t probes:local .
docker run -d -p 8080:10000 --name probes probes:local
curl http://localhost:8080/health/live
curl http://localhost:8080/api/status
```

The container listens on `${PORT:-10000}` with one Gunicorn worker and four threads.
To choose another container port, pass `-e PORT=9000 -p 8080:9000` instead of
`-p 8080:10000`. The direct `python3 app.py` development server still uses port `8080`.

SQLite defaults to `/app/data/health.db` inside the image. For local persistence,
add `--mount source=probes-data,target=/app/data` to `docker run` before the image name.
Without a volume, removing or replacing the container loses its database.

## Testing and CI

```bash
pip install -r requirements-dev.txt
ruff check .
pytest -q
```

Tests cover incident transitions and transaction rollback, concurrent failures, network errors,
environment configuration, Flask health routes, optional Telegram alerts, and checker shutdown.
They use isolated temporary databases and mocked target responses.

The workflow in [.github/workflows/ci.yml](.github/workflows/ci.yml) runs on pull requests
and pushes to `main`, using Python 3.12 and read-only repository permissions. Its checks are:

1. Ruff lint using the committed configuration and pinned development dependency.
2. `pytest -q`.
3. Docker image build with `--pull` to refresh the base image, tagged with the commit SHA.
4. Trivy filesystem and image scans, failing on HIGH or CRITICAL findings with available fixes.

The scan configuration follows the [Trivy action documentation](https://github.com/aquasecurity/trivy-action).
Fix reported findings before treating CI as passing; the workflow does not suppress individual
vulnerabilities. Successful local tests alone do not prove that the GitHub Actions build and scans pass.

Local verification on 2026-09-12 passed Ruff, all 74 tests, the Docker build, and both Trivy scans.
The initial image scan found 30 HIGH Debian package findings covering four CVEs. Rebuilding
with a freshly pulled base image cleared those findings under the same scan policy. See the
[scan investigation and image IDs](docs/CASE-STUDY.md#cached-base-image-scan-findings).
These are local results; the updated GitHub Actions workflow has not yet been verified by a run.

This workflow does not commit coverage badges or publish Docker Hub images and requires no
Docker Hub credentials. Render deployment remains separate and is not gated by these checks yet.
CI-gated deployment is still planned; do not describe this workflow as verified CI/CD until
the corresponding automation is implemented and its runs pass.

## Checker behavior

The checker measures HTTP reachability: responses below `500`, including `4xx`, count as up.
The first observation establishes a baseline without sending an in-app Telegram alert; an
initial failure still opens an incident. Later state changes send an alert after the database
transaction commits. Check samples and incident changes commit together, repeated failures
reuse the active incident, and recovery closes that target's active incident. Connections are
closed on both success and failure. SQLite writes wait up to five seconds for a lock; a failed
write is logged and the loop continues to the next target.

Target requests use a three-second connect timeout and five-second read inactivity timeout.
The checker closes responses after reading headers, without downloading target response bodies.
Latency uses a monotonic clock; incident duration uses UTC timestamps and is clamped to zero
if the wall clock moves backward. Logs use target names and error types, for example:

```text
event=health_check target="portfolio_api" status=down latency_ms=3001.200 error=ConnectTimeout
```

The interval wait is interruptible. Shutdown requests stop further checks, allow the current
check to finish, and wait up to 25 seconds for the checker thread. `gunicorn.conf.py` connects
this cleanup to worker exit; normal Python exit and the development server's SIGTERM handler
also request cleanup. Requests timeouts are not an overall deadline, so DNS resolution or
redirects can outlast that wait; an unfinished thread produces `event=checker_stop_timeout`.
See [Requests timeout semantics](https://requests.readthedocs.io/en/latest/user/quickstart/#timeouts).

## Configuration

Edit `services.yaml` to add or change monitored services. URLs support `${VAR_NAME}` substitution
from environment variables:

```yaml
check_interval_seconds: 240

services:
  - name: "My API"
    url: "${MY_API_URL}/health"
```

| Environment variable | Required | Purpose |
|---|---|---|
| `PORT` | No | Gunicorn container port; defaults to `10000`. Set by Render. |
| `DATABASE_PATH` | No | SQLite file; defaults to `health.db` locally and `/app/data/health.db` in Docker. Parent directories are created automatically. |
| `CHECK_INTERVAL_SECONDS` | No | Positive integer overriding `check_interval_seconds` in `services.yaml` (currently `240`; fallback `120`). Render configuration sets `60`. The checker waits this long after each check cycle. |
| `TELEGRAM_BOT_TOKEN` | No | Enables in-app Telegram alerts on status change |
| `TELEGRAM_CHAT_ID` | No | Destination chat for Telegram alerts |
| *(custom `${VAR}` names used in `services.yaml`)* | No | Resolved from the environment; unresolved vars fail their check gracefully rather than crashing |

## Deployment

The live application is deployed as a Docker-based Render Web Service to
avoid keeping paid AWS infrastructure running as a student.

The application was also deployed temporarily to Amazon EKS for Kubernetes
learning and incident debugging. The EKS cluster was deleted after testing
to control cloud costs.

## Render deployment

[render.yaml](render.yaml) defines the Docker service on the free plan, with
`PORT=10000`, `DATABASE_PATH=/app/data/health.db`, `CHECK_INTERVAL_SECONDS=60`, and
`/health/live` as its HTTP health check. The format follows the
[Render Blueprint reference](https://render.com/docs/blueprint-spec).

For the existing Render service, deploy the updated code and set the health-check
path to `/health/live` in its settings. Match the environment variables above and
clear any Docker command override so Render uses the Dockerfile's command.
Committing `render.yaml` alone does not update a service that is not managed by a Blueprint.
For a fresh setup, connect this GitHub repository through a Render Blueprint and
review the proposed service before applying it. See
[Render web service setup](https://render.com/docs/web-services).

The Telegram entries use `sync: false`; supply credentials privately only if using
in-app alerts. Leave them unset or empty when Grafana handles notifications.
Never commit real bot tokens or chat IDs. This configuration does not attach a
persistent disk; the storage limitation below still applies.

After deployment, verify:

```bash
curl --fail https://probes-794f.onrender.com/health/live
curl --fail https://probes-794f.onrender.com/health/ready
curl --fail https://probes-794f.onrender.com/health/startup
```

The existing Kubernetes lab manifests use port `8080`. When using this updated
image with those manifests, set `PORT=8080` in the container environment until
the lab manifests are updated together.

## Deploying to Kubernetes

The manifests in `k8s/` were used for a hands-on AWS EKS deployment (see the
[case study](docs/CASE-STUDY.md) for the full walkthrough, including a real Kubernetes networking
incident that came up during setup):

```bash
kubectl apply -f k8s/deployment.yaml -f k8s/service.yaml -f k8s/ingress.yaml
```

These assume an `nginx` Ingress controller is installed and a `probes-secrets` Kubernetes Secret
exists for the environment variables above.

## Prometheus/Grafana/Telegram integration

Prometheus scrapes `https://probes-794f.onrender.com/metrics`; Grafana queries the data,

The case study records a successful firing notification. Current configuration exports,

## EKS incident postmortem

During the temporary EKS lab, two running EC2 instances joined as `NotReady` nodes.
Investigation found the `aws-node` VPC CNI DaemonSet was missing; reinstalling the addon
was followed by both nodes becoming `Ready` within approximately one minute. An earlier
instance-type eligibility failure was a separate issue.

Read the [full postmortem](docs/eks-vpc-cni-incident.md) for the recorded investigation,
resolution, lessons, and evidence limitations.

## Storage limitation

The current deployment uses SQLite. Unless a persistent disk is attached,
local database contents may be lost when the Render service is recreated or
redeployed. This is acceptable for the current low-cost learning deployment.
PostgreSQL is the planned production-storage upgrade.

## Known limitations (left intentional, not overlooked)

- **No persistent storage in the Kubernetes deployment** — `health.db` lives on the pod's local
  disk. A pod restart wipes incident history. Documented and deliberately left this way to
  demonstrate the problem before reaching for a `PersistentVolumeClaim`. See the case study.
- **Single gunicorn worker by design** — the background checker thread runs once per process;
  scaling workers would duplicate pings. See the comment in `Dockerfile`.
- **In-app Telegram alerting is dormant** — real alerting is intentionally handled by an external
  Prometheus/Grafana stack instead, not hardcoded into the app. The code path still exists as a
  documented fallback.
